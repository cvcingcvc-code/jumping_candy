# Sentinel 智能体架构审计、安全修复与迭代推进方案

## 一、 项目背景与架构综述

Sentinel（哨兵）是一款基于大模型与规则引擎双轨驱动的网络安全流量分析智能体。系统旨在提供从**数据输入**到**攻击识别**、**来源研判**、**归属地追踪**和**安全报告生成**的闭环能力。

### 1.1 双轨运行架构

```
                      ┌────────────────────────────────────────┐
                      │            用户数据源输入              │
                      │ (结构化文本日志 / 本地文件监视 / 端口监测) │
                      └───────────────────┬────────────────────┘
                                          │
                  ┌───────────────────────┴───────────────────────┐
                  ▼                                               ▼
     【浏览器端纯静态工作台 (web/)】               【Python + FastAPI 后端 (backend/)】
   - 无需后端，直接运行在浏览器                   - LangGraph 编排工作流
   - 内置纯 JS 离线规则引擎 (engine.js)           - 节点分流：triage → capture/parse
   - 快照差分实时告警中心 (alerts.js)             - 核心引擎：detect → geolocate → report
   - 浏览器本地缓存 + 可选 ipwho.is 情报          - DeepSeek 大模型研判（无 Key 降级为离线模板）
   - 适合静态托管（GitHub Pages / CDN）           - 适合服务端深度分析与多轮交互
```

### 1.2 关键安全设计准则
- **杜绝原始二进制文件输入**：系统从架构层面拒绝解析 `.pcap`、`.pcapng`、`.exe` 等二进制文件，规避隐藏在原始数据包或可执行文件中的恶意载荷执行风险；要求使用 `tshark`/`tcpdump` 转为结构化文本日志（CSV/JSON/Log）后再输入。
- **离线规则与大模型深度互补**：规则引擎负责客观特征提取与时序统计；大模型负责高阶威胁归因、语义分析与加固建议撰写。未配置 API Key 时系统完整平滑降级至离线模板。

## 二、 首轮代码与安全审计成果

在本轮审计中，对全栈代码进行了语法分析、测试验证及边界安全检查，共发现并彻底修复了 4 项高危逻辑缺陷（P0）与 3 项工程/安全缺陷（P1）：

### 2.1 P0 缺陷修复清单

1. **暴力破解误报漏洞 (`backend/tools/detector.py`)**：
   - **缺陷**：原逻辑 `failed = status in (401, 403, 200)` 将 HTTP 200 OK（成功登录）判定为认证失败，导致合法管理员正常连续登录被误报为暴力破解攻击（`brute_force`）。
   - **修复**：严格剔除 200/302 等成功状态码，仅统计 401/403 及无状态认证端口连接，与前端 `engine.js` 判定基线统一。

2. **敏感路径探测误报漏洞 (`backend/tools/detector.py`)**：
   - **缺陷**：仅按单一源 IP 的命中次数累加，导致用户正常刷新同一后台页面（如 3 次 `/admin`）即被判定为恶意扫描。
   - **修复**：建立集合跟踪不同路径，要求同一来源必须探测至少 3 个**互不相同**的敏感路径（如 `/.git`、`/.env`、`/phpmyadmin`）才触发 `sensitive_path_probe`。

3. **模拟演练与真实入侵混淆缺陷 (`backend/tools/reporter.py`)**：
   - **缺陷**：当环境缺乏网卡权限回退为沙箱模拟流量时，报告研判依然下达“研判为真实攻击”的结论，存在严重技术误导。
   - **修复**：捕获 `capture_meta.simulated` 标志，研判结论强制加注【模拟演练】前缀，报告正文明确提示演练性质，输出结构显式返回 `is_simulated: true`。

4. **IP 溯源过度表述与局限性免责 (`backend/tools/reporter.py`)**：
   - **缺陷**：原报告将公网 IP 定位直接表述为攻击者物理归属地，忽视了代理、VPN、CDN 与跳板机对出口 IP 的混淆。
   - **修复**：全量增加免责与技术局限性说明（Disclaimer），明确 IP 归属地仅代表网络出口节点，不可等同于攻击者真实物理位置。

### 2.2 P1 安全与架构增强

1. **双重 URL 编码防御 (`backend/tools/detector.py`)**：引入最多 2 次的安全递归解码（`safeDecode`），防御 `%253cscript`、`%253bcat` 等二次编码载荷绕过。
2. **打通 FastAPI 与静态工作台 (`backend/main.py`)**：在后端挂载 `/web` 路由，支持单一进程同时访问交互式 API 与纯前端取证工作台。
3. **API 入参范围与路径穿越加固 (`backend/schemas.py`, `backend/main.py`)**：Pydantic 校验端口范围（1-65535）、抓包时长（1-300 秒），升级文件读取使用 `relative_to` 与 ID 正则白名单。

## 四、 下一阶段迭代推进路线（Roadmap）

为了让 Sentinel 具备更强的生产可用性与多场景落地能力，制定以下三阶段迭代推进方案：

### Phase 1：规则与签名统一配置化（近期重点）
- **目标**：消除 Python 后端与 JS 前端规则重复维护的技术债。
- **具体实施**：
  1. 将硬编码在 `backend/tools/detector.py` 与 `web/assets/engine.js` 中的恶意特征、工具指纹、敏感路径抽取至统一的 `config/signatures.json`。
  2. Python 端与前端引擎均通过 JSON 动态加载规则，实现“一份规则，双端同步”。
  3. 支持用户自定义规则热加载（Custom Signatures）。

### Phase 2：智能体记忆持久化与流式大文件处理（工程强化）
- **目标**：提升生产环境高并发与长时间网络监控支持能力。
- **具体实施**：
  1. **SQLite 记忆持久化**：将 `backend/agent/memory.py` 的内存 `MemorySaver` 升级为持久化 `SqliteSaver`，实现服务重启后会话上下文与多轮追问不中断。
  2. **流式分块分析（Streaming Analytics）**：针对长时间真实抓包导出的超大 CSV/日志（50MB~500MB），引入流式处理管道与生成器，降低内存占用，避免服务 OOM。
  3. **后端健康检查扩展**：在 `/api/health` 中增加真实网卡可用性、pcap 驱动依赖、GeoIP 库状态检测。

### Phase 3：云端与多模型融合增强（智能化扩展）
- **目标**：拓展研判模型生态与云端自动化部署。
- **具体实施**：
  1. **多大模型兼容支持**：除 DeepSeek 外，增加对 Gemini 1.5/2.0、Claude 等主流模型的原生 API 支持与动态切换。
  2. **MITRE ATT&CK 攻击链图谱可视化**：在前端报告中将多项 findings 自动聚合映射为攻击链阶段（Reconnaissance → Initial Access → Execution → Exfiltration），提供交互式攻击演进图谱。
  3. **自动化容器部署**：提供标准的 `Dockerfile` 与 `docker-compose.yml`，支持一键容器化交付，提供完整的非 root 运行沙箱环境。
